# 01-init：调查研究与任务卡

> **"没有调查，没有发言权"** — 不读代码库就不许提方案。

## 职责

先调查代码库，再帮用户理清思路，然后澄清需求，把用户需求压缩成**可检查、可执行、可回滚**的任务卡。

<硬门禁>
在用户批准设计之前，不允许进入任何实现阶段、写任何代码、创建任何项目脚手架。无论任务看起来多简单都必须经过澄清。澄清之前必须先调查代码库。
</硬门禁>

## 反模式："这太简单了不需要澄清"

每个任务都要走澄清流程。一个 todo 列表、一个单函数工具、一个配置变更——全部都要。"简单"任务恰恰是未审视的假设造成最多返工的地方。澄清可以很短（真正简单的任务几句话就够），但必须做。

---

## 交互规则

**所有需要用户选择或确认的地方，必须直接调用 AskUserQuestion 工具弹出选择框。**

**禁止行为**：
- 在回复文字中列出选项等用户打字回复
- 用 markdown 列表展示选项
- 写"请回复 A/B/C"之类的文字

**正确行为**：
- 直接调用 AskUserQuestion 工具
- 问题明确，选项 2-4 个
- 用户选择后立即继续流程

---

## 流程

### Step 0：会话上下文加载（恢复场景）

> 如果是从上一会话恢复，必须先加载上下文再开始工作。

**触发条件**：用户说"恢复"/"继续"/"从checkpoint恢复"或提供了checkpoint_id

**方法**：

1. 扫描 `docs/handoffs/` 目录查找最近的交接文档
2. 读取交接文档中的「上下文包」（5类信息：决策/进展/代码状态/待办/失败尝试）
3. 读取 `phase_memory_card.md` 中的「恢复优先级」，按顺序加载关键文件
4. 验证现场一致性（git分支、文件是否存在）
5. 向用户确认恢复点后继续

**无交接文档 → 跳过此步骤，进入 Step 1**

**上下文效率规则**（恢复场景或新会话均适用）：

从上一会话恢复时，上下文空间有限，必须高效利用：

1. 读取 `safeguards/context.md` 中的分层加载规则
2. 按L0→L1→L2→L3优先级加载，不要一次性读取所有文件
3. 恢复时只加载L0（任务卡+目标）和L1（当前任务相关文件）
4. L2/L3按需加载，不要预读

### Step 1：调查研究（代码库调查）

> **"没有调查，没有发言权"** — 先读代码，再提问。

**目标**：理解当前项目状态和代码库全貌，避免在信息不足的情况下提问。

**方法**：

| 动作 | 具体操作 | 工具 |
|------|----------|------|
| 检查项目结构 | 读取根目录、关键配置文件 | LS / Read |
| 识别技术栈 | 从 package.json / Cargo.toml / pyproject.toml 等推断 | Read |
| 定位相关代码 | 搜索与任务相关的文件和模块 | Grep / Glob / SearchCodebase |
| 识别已有模式 | 找到可复用的代码模式 | Grep（搜索相似实现） |
| 理清依赖关系 | 读取 import/require，构建依赖图 | Read |
| 检查 GSD 上下文 | 有 `.plans/` 则读取 STATE.md 和 active/PLAN-*.md | Read |
| 检查最近变更 | 查看最近的 git 提交或文件修改 | Grep / Read |

**产出**：代码库调查报告（内部使用，包含技术栈、相关文件、可复用模式、依赖关系）

### Step 2：范围评估

**目标**：判断任务是否需要拆分为多个子项目。

**方法**：检查用户请求是否描述了多个独立子系统。

**判断标准**：
- 如果请求包含"和"连接的多个独立功能（如"做一个带聊天、文件存储、计费和分析的平台"），立即标记
- 每个子项目应该能独立产出可工作、可测试的软件
- 子项目之间有明确的依赖顺序

**处理方式**：
- 需要拆分 → 调用 AskUserQuestion，问题"这个请求包含多个独立功能，建议拆分为X个子项目，是否同意？"，选项"同意拆分"/"不需要拆分，继续作为一个项目"
- 不需要拆分 → 继续下一步

### Step 3：思路梳理

> **"先理清思路，再明确需求"** — 用户很多时候自己还没想清楚要什么，直接问"你想解决什么问题"是无效的。

**目标**：帮用户从混沌状态进入清晰状态，确保在提问澄清之前，用户已经想清楚自己要什么。

**核心方法**：复述→追问→具象化→确认

**3.1 复述理解**

把用户的原始需求用自己的话复述一遍，让用户确认理解是否正确。

调用 AskUserQuestion：
- 问题："我理解你的需求是：[复述内容]，这个理解对吗？"
- 选项："对，就是这个意思" / "不完全对，我补充一下" / "完全不对，我重新说"

**3.2 追问本质**

通过追问找到需求背后的真实动机。

调用 AskUserQuestion：
- 问题："你想要这个功能的根本原因是？"
- 选项："解决现有痛点" / "抓住新机会" / "规避风险" / "其他原因"

如果用户选"解决现有痛点"，继续追问："具体是什么痛点？"
如果用户选"抓住新机会"，继续追问："具体是什么机会？"
如果用户选"规避风险"，继续追问："具体是什么风险？"

**3.3 具象化场景**

把抽象需求变成具体场景，让用户能看到画面。

调用 AskUserQuestion：
- 问题："如果这个功能做好了，你会在什么场景下使用？"
- 选项："日常开发时（高频使用）" / "特定场景偶尔使用（低频但关键）" / "演示/展示用" / "其他场景"

**3.4 确认思路清晰度**

调用 AskUserQuestion：
- 问题："现在你的思路清晰了吗？"
- 选项："清晰了，可以继续明确需求细节" / "还不够清晰，需要继续讨论" / "我需要换个角度重新想"

**思路不清晰时的处理**：
- 用户选"继续讨论" → 回到 3.2，换个角度追问
- 用户选"换个角度" → 从不同维度重新梳理（技术视角/用户视角/业务视角）
- 最多循环 3 次，3 次后仍不清晰 → 建议用户先想清楚再继续，不要硬推

**关键原则**：
- 不在用户思路不清时推进到需求澄清
- 不替用户做决定
- 帮用户发现自己的真实需求
- 用具体场景代替抽象描述

### Step 3.5：业务背景挖掘门禁

> 解决P-015业务理解缺失：AI不能只接受字面指令，必须主动理解业务背后的"为什么"。

**触发条件**：用户提出新任务/新功能时自动触发

**执行动作**：

1. 读取 `safeguards/understanding.md`
2. 从8个维度中主动追问至少3个（用户是谁/业务目标/成功指标/现有流程/边界条件/关联系统/数据流向/非功能需求）
3. 评估理解深度：
   - 🟢 覆盖≥5个维度 → 可以进入Step 4
   - 🟡 覆盖3-4个维度 → 补充追问1-2轮
   - 🔴 覆盖<3个维度 → 必须继续追问，不能跳过
4. 如用户提供了需求文档，按「需求文档自检清单」检查文档质量

**关键原则**：理解深度不足时，不许进入Step 4逐个提问澄清

### Step 3.5b：元认知自检门禁

> 解决P-015业务理解缺失/P-053理解债/P-054主观偏差：在输出任何内容前，强制自检信息完整性。

**触发条件**：Step 3.5业务背景挖掘完成后、进入Step 4之前自动触发

**执行动作**：

1. 读取 `safeguards/meta-cognition.md`
2. 执行五维信息审视（重点维度1意图 + 维度2约束）
3. 标记所有 🔴 缺口
4. 有 🔴 缺口 → 先向用户确认，补充信息后再进入Step 4
5. 无 🔴 缺口 → 进入Step 4

**自检示例**：
```
【元认知自检】
维度1（意图）：用户要"优化代码"——"优化"是歧义词，未确认是性能还是可读性 → 🔴
维度2（约束）：用户未提及时间约束和技术栈约束 → 🔴
维度3（上下文）：已读取相关文件 → ✅
维度4（假设）：假设用户要性能优化——无证据支持 → 🔴
维度5（歧义）："优化"=歧义，"尽快"=无时间标准 → 🔴
→ 4个🔴缺口，必须先向用户确认
```

**关键原则**：有🔴缺口时不许进入Step 4，不许"猜测"执行

### Step 3.6：专项评估门禁

> 解决P-038中文编码/P-054主观偏差/P-075入门路径：根据项目特征按需加载专项防护。

**触发条件**：Step 3.5业务背景挖掘完成后自动评估

| 评估维度 | 触发条件 | 加载文件 | 检查重点 |
|----------|----------|----------|----------|
| 中文开发者适配 | 目标用户包含中文用户/团队在国内 | `safeguards/chinese-dev.md` | 中文编码规范/文档适配/生态差异 |
| 认知偏差校准 | 开发者首次使用AI辅助/对AI能力有误解 | `safeguards/bias-calibration.md` | 主观偏差校准/监督者角色防护 |
| 人才梯队保护 | 团队有初级开发者/任务可分级 | `safeguards/talent-pipeline.md` | 入门路径保护/知识传承机制 |

**执行方式**：按触发条件逐项评估，满足条件则加载对应safeguard执行检查，不满足则跳过

### Step 4：逐个提问澄清

**目标**：通过苏格拉底式对话，摸清用户真实意图。

**核心原则**：
- **一次只问一个问题** — 每次只调用一次 AskUserQuestion
- **优先选择题** — 能用选择题就不用开放题
- **聚焦三个维度** — 目的（Purpose）、约束（Constraints）、成功标准（Success Criteria）

**提问维度与典型问题**：

| 维度 | 典型问题 | 选项示例 |
|------|----------|----------|
| **目的** | 你想解决什么问题？ | A) 提升性能 B) 增加功能 C) 修复 Bug D) 其他 |
| **用户** | 谁会使用这个功能？ | A) 开发者 B) 终端用户 C) 内部团队 D) 其他 |
| **约束** | 有什么不能动的？ | A) 不能改数据库 B) 不能加依赖 C) 不能改 API D) 其他 |
| **成功标准** | 怎么算做成了？ | A) 测试通过 B) 页面可访问 C) 性能提升 50% D) 其他 |
| **边界** | 什么不在范围内？ | A) 不做移动端 B) 不做权限 C) 不做国际化 D) 其他 |
| **优先级** | 如果只能做一部分？ | A) 核心功能优先 B) 用户体验优先 C) 安全优先 D) 其他 |

**提问节奏**：
1. 先问目的（1-2 个问题）
2. 再问约束和边界（1-2 个问题）
3. 最后确认成功标准（1-2 个问题）
4. 总计 3-6 个问题，不要超过 8 个

**信息充分判断**：
- 目的明确 + 约束清晰 + 成功标准可检查 → 停止提问
- 任何一个维度模糊 → 继续追问
- 关键信息缺失（验收/边界/权限/环境） → 必须回问，不允许猜

### Step 5：提出 2-3 个方案

**目标**：让用户看到不同路径的权衡，而不是只有一个选择。

调用 AskUserQuestion：
- 问题："以下是 2-3 个实现方案，你倾向哪个？"
- 选项：
  - "方案 A（推荐）：[方案名] — [一句话描述]。优势：[核心优势]。代价：[核心代价]"
  - "方案 B：[方案名] — [一句话描述]。优势：[核心优势]。代价：[核心代价]"
  - "方案 C：[方案名] — [一句话描述]。优势：[核心优势]。代价：[核心代价]"

**原则**：
- 先说推荐方案和理由
- 每个方案必须包含代价/风险，不能只说好处
- YAGNI（你不需要它）：从所有方案中砍掉不必要的功能

### Step 6：分段展示设计

**目标**：让用户逐步确认设计，而不是一次性审批一大段文字。

**方法**：按以下维度分段说明，每段调用一次 AskUserQuestion 等用户确认：

| 段落 | 内容 | 粒度 |
|------|------|------|
| 架构 | 整体方案、模块划分、数据流 | 2-3 句话（简单）/ 200-300 字（复杂） |
| 组件 | 每个模块的职责和接口 | 每个组件一段 |
| 错误处理 | 失败场景和恢复策略 | 关键场景一段 |
| 测试 | 验证策略 | 一段 |

**每段展示后**：

调用 AskUserQuestion：
- 问题："以上是[架构/组件/错误处理/测试]设计，这部分看起来对吗？"
- 选项："对，继续下一段" / "不对，需要修改"

**用户说不对 → 回到 Step 4 补充澄清**
**用户说对 → 继续下一段**

### Step 7：生成任务卡

**目标**：把澄清结果压缩为结构化任务卡。

**任务卡结构**：

```yaml
goal: "一句话目标"
done_definition:
  - "DoD 1：[可检查的验收条件]"
  - "DoD 2：[可检查的验收条件]"
  - "DoD 3：[可检查的验收条件]"
constraints:
  - "约束 1"
  - "约束 2"
risks:
  - "风险 1"
non_goals:
  - "不在范围内的事 1"
  - "不在范围内的事 2"
```

**DoD 检查清单**：
- [ ] 至少 3 条 DoD
- [ ] 每条 DoD 都是可检查的（能回答"通过/未通过"）
- [ ] 没有模糊词（如"优化"/"改进"/"提升"——必须量化或具体化）
- [ ] non_goals 明确列出了不在范围内的事

### Step 8：任务卡自检

**目标**：确保任务卡没有遗漏和矛盾。

**自检项**：

| 检查项 | 说明 |
|--------|------|
| 占位符扫描 | 有没有"TBD"/"TODO"/"待定"？有则补齐或删除 |
| 内部一致性 | goal 和 done_definition 是否矛盾？constraints 和 non_goals 是否冲突？ |
| 范围检查 | 任务卡是否聚焦到单个可执行计划？还是需要拆分？ |
| 歧义检查 | 有没有可以有两种理解的表述？有则选一种并明确 |

**发现问题 → 当场修复，不需要重新走流程**

### Step 9：用户审批

**目标**：让用户最终确认任务卡。

调用 AskUserQuestion：
- 问题："任务卡已生成。请确认 goal、DoD、约束和非目标是否准确。"
- 选项："确认，进入计划阶段" / "需要修改"

**用户选"需要修改" → 回到 Step 4 补充澄清，更新任务卡**
**用户选"确认" → 进入 Step 10**

### Step 10：项目初始化（可选）与状态同步

如果项目没有 `.plans/` 目录，使用模板创建：

1. 创建 `.plans/` 目录
2. 使用 `templates/gsd_project.md` 创建 `PROJECT.md`
3. 使用 `templates/gsd_requirements.md` 创建 `REQUIREMENTS.md`
4. 使用 `templates/gsd_roadmap.md` 创建 `ROADMAP.md`
5. 使用 `templates/gsd_state.md` 创建 `STATE.md`

同步 GSD 状态：更新 `.plans/STATE.md`

## 产物

- 任务卡（包含 goal / done_definition / constraints / risks / non_goals）
- 至少 3 条可检查的 DoD
- 明确的 non_goals（不在范围内的事）

## 路由

- 任务卡完成且用户确认 → 进入 `components/02-plan/SKILL.md`
- 信息不足 → 继续澄清，不跳过
- 范围过大 → 拆分为子项目，对第一个子项目重新走澄清流程
