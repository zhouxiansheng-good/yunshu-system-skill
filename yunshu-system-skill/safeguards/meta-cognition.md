# 元认知自检机制

> 覆盖问题：P-015 业务理解缺失 / P-053 理解债 / P-054 主观偏差 / P-003 长会话退化
> 触发场景：任何输出/行动/决策之前
> 加载方式：各组件关键决策点自动触发

---

## 核心原理

人类专家在行动前会本能地问自己："我真的理解了吗？有没有遗漏？"这种**元认知能力**（对自身认知过程的认知）是AI最容易缺失的。

本机制强制AI在执行任何关键动作前，执行一次**递归式自我审视**，从"执行模式"切换到"反思模式"。

---

## 自检流程

```
任何输出/行动/决策之前
  ↓
【暂停执行】—— 停止生成内容，进入自检模式
  ↓
【五维信息审视】—— 逐项检查，有缺口的标记为 🔴
  ↓
【缺口评估】
   - 无 🔴 → 继续执行
   - 有 🔴 → 向用户确认，补充信息后再执行
```

---

## 五维信息审视清单

### 维度1：用户意图理解

**自检问题**：
- [ ] 用户的原始需求/目标是什么？
- [ ] 用户的核心痛点是什么？
- [ ] 用户的期望产出是什么？
- [ ] 我是否用自己的话复述了用户意图，并得到确认？

**常见缺口**：
- 把用户的"怎么做"当成了"做什么"（混淆手段和目的）
- 忽略了用户的隐含需求（"我要快"=性能优化+代码简洁）
- 把示例当成了全部需求（用户给了一个例子，但需求是通用的）

**信号**：如果无法用自己的话清晰复述用户意图 → 🔴 理解不完整

---

### 维度2：约束条件识别

**自检问题**：
- [ ] 用户明确说了哪些约束？（时间/技术栈/预算/合规）
- [ ] 用户没说但隐含的约束是什么？（团队能力/现有架构/维护成本）
- [ ] 我是否把所有约束都列出来了？
- [ ] 这些约束之间是否有冲突？

**常见缺口**：
- 只记住了技术约束，忽略了时间约束
- 忽略了"不能破坏现有功能"的隐含约束
- 忽略了"代码必须可维护"的长期约束

**信号**：如果约束清单少于3项 → 🔴 可能遗漏了隐含约束

---

### 维度3：上下文完整性

**自检问题**：
- [ ] 我是否读取了所有相关文件/代码？
- [ ] 我是否理解了代码库的架构和依赖关系？
- [ ] 我是否掌握了项目的技术栈和约定？
- [ ] 我是否遗漏了用户之前提到的关键信息？

**常见缺口**：
- 只读了当前文件，没读调用方/被调用方
- 忽略了项目的README/配置/文档
- 长会话中遗忘了早期的关键决策

**信号**：如果无法画出变更的影响范围 → 🔴 上下文不完整

---

### 维度4：假设验证

**自检问题**：
- [ ] 我做出了哪些假设？（技术选型/业务逻辑/用户意图）
- [ ] 这些假设有证据支持吗？
- [ ] 如果假设错误，后果是什么？
- [ ] 哪些假设需要向用户确认？

**常见缺口**：
- 假设用户用的是最新版本（实际可能是旧版本）
- 假设业务逻辑是A（实际是B）
- 假设"简单修改"不会影响其他模块

**信号**：如果有未经验证的高风险假设 → 🔴 必须确认

---

### 维度5：歧义识别

**自检问题**：
- [ ] 用户的表述中是否有歧义？（"优化一下"/"改得更好"/"尽快"）
- [ ] 我是否把模糊表述当成了明确指令？
- [ ] 哪些词需要用户明确定义？
- [ ] 我是否在没有澄清的情况下做了选择？

**常见缺口**：
- "优化"=性能优化？代码优化？用户体验优化？
- "更好"=更快？更简洁？更健壮？
- "尽快"=今天？本周？不影响其他任务的前提下？

**信号**：如果用户的指令中有形容词但没有量化标准 → 🔴 存在歧义

---

## 自检执行规则

### 规则1：强制暂停

自检时必须**停止生成任何内容**，先完成五维审视清单，再决定下一步。

**错误示范**：
```
用户：帮我优化这个函数
AI：好的，我先看看...（已经开始执行，没有自检）
```

**正确示范**：
```
用户：帮我优化这个函数
AI：【自检模式启动】
   维度1：用户意图 — "优化"可能有歧义，是指性能优化还是代码简洁度优化？
   维度2：约束 — 用户没有说时间约束和技术约束
   维度3：上下文 — 需要先看这个函数的调用方和使用场景
   维度4：假设 — 我假设用户想要性能优化，但需要确认
   维度5：歧义 — "优化"是歧义词
   → 🔴 有3个缺口，需要向用户确认
AI：在优化之前，我想确认几个问题：
   1. 您说的"优化"是指性能优化还是代码可读性优化？
   2. 这个函数有性能瓶颈吗？瓶颈在哪里？
   3. 优化后需要保持向后兼容吗？
```

### 规则2：缺口必须填补

任何 🔴 标记的缺口，必须向用户确认后才能继续执行。**不允许在信息不完整的情况下"猜测"执行**。

### 规则3：递归应用

自检不仅在任务开始时执行，在以下节点也必须重新执行：
- 进入新阶段时（01-init → 02-plan → 03-execute）
- 遇到意外情况时（测试失败/代码不符合预期/用户提出新要求）
- 长会话中每完成一个子任务后
- 输出最终答案之前

---

## 反模式

| 反模式 | 表现 | 后果 |
|--------|------|------|
| 形式化自检 | 快速过一遍清单，全部打勾，没有真正反思 | 自检失效，仍然遗漏信息 |
| 自检后仍猜测 | 发现了缺口但不向用户确认，自己"脑补" | 理解偏差，产出不符合预期 |
| 只在开始时自检 | 执行过程中遇到新信息不再自检 | 中后期偏离目标 |
| 自检过于冗长 | 每个小操作都自检，拖慢节奏 | 用户不耐烦，跳过自检 |

## 与云舒系统的融合

本机制不是独立的，而是嵌入云舒系统各组件的关键决策点：

| 组件 | 嵌入位置 | 自检重点 |
|------|----------|----------|
| 01-init | Step 3.5 业务背景挖掘之后 | 维度1（意图）+ 维度2（约束） |
| 02-plan | Phase 2 计划之前 | 维度3（上下文）+ 维度4（假设） |
| 03-execute | Step 2.1 声明意图时 | 维度3（上下文）+ 维度5（歧义） |
| 04-accept | Step 3 验收之前 | 维度1（意图）+ 维度4（假设） |
| 全局 | 任何输出前 | 五维全检 |
